## 2. Balance Policy and Operation Identity

OK, I'll clarify some of the questions: 1. Balance policy: Not allow negative balances. In case you are asking to withdraw an amount bigger than the balance. Return an error. Take in account that in order to work properly, checking the balance and subtracting the amount should be atomic operations, to avoid concurrency issues. 2. Idempotency: Transaction Ids should be global. Transaction Ids are not generated by a succesful transaction, but from a user balance operation. Maybe we can split between operationid and transactionid? so the transaction is is generated after the actual operation has been accepted by the idempotency control.

## 3. Declined Operation Retries

Clarifyin 2. Yes, a retry with the same operationID should give a decline. We consider that the frontend only reuses the operationID when it's retrying automatically, new user interactions generate a new operation id.

## 4. Account Service and Ownership

Clarifying 3., we should have another service, for Accounts, that allows CRUD operations for accounts. All accounts start with a balance of 0. A user can have multiple accounts. An operation can only be executed against an account that is owned for the user currently authorised (logged in)

## 5. Account Updates and Closure

Confirming behaviour for the account service: The service assigns unique account numbers. No transfer of ownership is on scope for now. Updates cannot change balance, number or owner. Account deletion actually only disabled the account, so no new operations can be executed over it, but you can list transactions. Closure with remaining balance should autogenerate a withdrawal operation with the remaining balance.

## 6. External Withdrawals and Reactivation

We can assume that the withdrwal operation means that money is returned to an external destination, but for now this is transaparent to us. Regarding reactivation, we could reactivate an account, but it'll not cause any further change in the balance

## 7. Credential Handling

Regarding the user service, some more clarications: I accept the credentials being sent only by https, and the salting on the server, and no accepting client-provided saltedhashedpassword. Also, never log any password, stored hashes or access tokens.

## 11. Disabled-Account Operations

I also accept this: a retry of an already completed balance operation after closure returns its recorded outcome, subject to ownership checks, without executing a new operation. A new operation against a disabled account returns `409 Conflict` with code `ACCOUNT_DISABLED`. A disabled account may be reactivated without any change to its balance.

## 12. Closure Retries and Identity

I also accept repeated or concurrent closure requests return the disabled state and the same closure result without generating another withdrawal. The internally generated closure `operationId` and resulting `transactionId` are globally unique and preserved for retries and history.
